# 新闻事件流

新闻批次已部署并验收，旧数据迁移、重启、两端页面及 65 分钟采集和资源观察通过。复用已授权的华尔街见闻快讯和 TrendRadar SQLite 采集。可选 AI 解读单独排队，默认关闭，已完成单次真实业务调用验收；见 [AI 解读接口](ai-api.md)。

## 读取接口

均位于 `/finevent/api/v1/`，使用现有单用户会话和 `no-store` 响应；未登录返回 401。

| GET 路径               | 内容                                                                                 |
| ---------------------- | ------------------------------------------------------------------------------------ |
| `news`                 | 每页 30 条报道，`items`、`next`、`watermark`、分类积压 `backlog`                     |
| `news/{id}`            | 当前来源全文、分类依据、最多 30 版旧修订、跨源关联及查找范围；不存在或已清理返回 404 |
| `news/meta`            | 类别、提及行业、留存来源、采集开关、服务器时间及两条采集通道的成功/失败/缺口记录     |
| `news/collection`      | 最近 20 轮华尔街见闻轮询及逐页响应证据，`next` 为下一页的 `before` 游标，0 表示结束  |
| `news/changes?after=N` | 从水位开始的新增、修订、分类更新或删除；返回 `changed`、`watermark`、`reset`         |

列表支持 `source`、`category`、`industry`、`importance`（0 全部、2 关注及以上、3 重要）、`q`（标题/正文的文字包含，最多 100 字）、`since`（首次发现时间下界，Unix 秒），以及 `order=discovered|published`。分类额外支持 `unclassified`，不包括尚未处理的报道。非法参数返回 400。

`next` 原样作为下一页 `cursor`，并保持其他筛选不变。采用时间/ID 游标及首次查询的最大 ID，避免新消息在翻页时挤入；修订可能改变排序或筛选命中，刷新可重新读取。来源发布时间为 0 时显示未知，按发布时间排序时置后。列表不返回正文，详情按需读取。

可见页面每 30 秒读取变更水位和通道状态。新消息以“更新当前内容”提示呈现，保留阅读位置及未提交筛选；用户刷新后重新读取当前已应用条件。水位失效时也提示重载。详情链接使用 `/finevent/#news=123`，登录后继续定位；返回列表恢复筛选及可用的标题焦点。

## 证据与分类

- 来源 ID 相同的跨日重复采集更新同一条记录；标题、正文、链接或发布时间变化留下旧版。重复采到但内容不变不制造变更通知。
- 规范化链接去除追踪参数；相同链接作为跨源证据关联。正文去空白、忽略大小写后计算指纹，至少 40 字且首次发现相距不超过 36 小时才作相同正文关联。两种精确关联合计最多 30 条。
- 相似标题只作待核对关联：首次发现相距 72 小时内、其他来源最近 200 条候选、标题前 300 字、双字相似度至少 82%，且数字和主要反向/否定词一致；最多展示 10 条。各来源正文及版本独立保留，不据相似标题删除报道。关联不代表独立事实核实，也不证明覆盖完整。
- 十个一级类别沿用技术设计，额外标记文本提及的行业和规则重要性。关键词、版本和命中依据见 `apps/server/internal/news/rules.go`。规则只能筛选主题，可能误匹配；提及行业不等于受到影响，重要性不表示利好/利空。无命中保持未分类，不虚构事实摘要、实际值、预期或前值。
- 来源发布时间、首次记录、入库、最近内容更新和最近采集分别保存。`first_seen` 沿用既有采集语义：直采为 finevent 首次发现，TrendRadar 为其数据库的首次记录；页面对应标明“上游首次记录”，finevent 实际接收另看入库时间。旧数据没有入库/更新时间时保持未知，旧修订没有链接/发布时间证据时保持未知；不从抓取时间反推发布时间。
- 通道状态显示最近尝试、最近成功及历史缺口。后续成功不自动关闭旧缺口；TrendRadar 导入成功不等于其各个上游来源健康。逐源健康展示见 [来源健康接口](source-health-api.md)，持续故障评估见 [实施状态](implementation-status.md#仍待完成)。

## 采集重试与延迟证据

华尔街见闻正常采集间隔为两分钟，每轮最多四页，单请求仍为 15 秒期限。超时、网络中断、正文读取失败和服务端 5xx 后，按连续失败次数等待 30、60、120、240、300 秒；持续失败上限为五分钟。429 至少等待五分钟，429/503 的有效 `Retry-After` 可延长等待。格式错误、其他 HTTP 错误和没有分类的旧失败记录沿用至少五分钟；完整成功后恢复正常周期。计时从上一轮完成开始，实际触发还受十秒调度节拍和请求耗时影响，不承诺所有新闻均在五分钟内发现。补采请求失败可触发短重试，但本轮已入库条目和历史缺口分别保留。TrendRadar 导入及 AI 调用的调度不变。

`GET news/collection?before=<轮询ID>` 按轮询 ID 倒序分页；省略 `before` 读取最新记录。每轮的 `requests` 按请求顺序保存毫秒起止时间、分页 cursor、HTTP 状态、失败类别、重试期限、读取字节数、完整性标志、响应 SHA256，以及实际返回的条目 ID/发布时间；不保存响应正文或请求凭据。每页最多记录 100 项，超过时 `items_truncated=true`，`item_count` 仍是原始项数。正文不完整或失败时不能用空列表推断来源没有新闻。摘要只标识实际读取的字节，不代替原始全文证据。

逐页证据保留七天，轮询结果保留三十天；证据与对应轮询同事务写入。旧记录、清理后的记录或入库后进程中断而尚未保存的轮询不能补造证据。两个成功、未截断窗口的 ID 和时间变化可以帮助核查迟到条目和发布时间修订，但仅代表已观察窗口；不能据此断言上游完整覆盖或故障根因。后续恢复不自动补证旧缺口。

验证工作台的延迟统计使用首次发现时的来源发布时间：当前版本为 1 时使用当前值，发生修订后使用已保存的第 1 版时间。缺少第 1 版证据的旧记录计为未知，后续发布时间修订不再改写历史延迟。新闻详情继续显示来源最新时间和修订记录。

## 存储与运行

新报道在入库事务内同步生成规则分类；历史记录或规则版本变化加入持久化索引队列，每秒最多处理 25 条，重启继续。分类未就绪的条目仍可阅读，页面提示筛选可能暂不完整。索引及队列与新闻共用独立 SQLite，没有额外常驻服务。

迁移保留旧版 `news_revisions` 的五列结构；新增版本链接和发布时间放入 `news_revision_evidence`，避免破坏上一版本的原位回滚写入。数据库触发器和独立编号记录防止清理后重用新闻编号，也覆盖旧版程序写入；已删除的详情链接不会指向另一条新闻。回退期间产生的版本会在再次升级时重建分类，无法证实的更新时间恢复未知。新闻和修订沿用最近采集超过 90 天的清理规则；分类、证据及排队项随所属新闻清理，变更日志保留 90 天。AI 解读输入快照独立保存至少一年，普通新闻清理不删除它，部署与验收记录见 [实施状态](implementation-status.md)。

本地 E2E 的新闻接口使用明确测试夹具；真实 SQLite、迁移、采集写入和 API 由 Go 回归覆盖。生产验收已核对 12,343 条旧新闻保全及索引积压清空，完成重启和 65 分钟观察；服务内存峰值 45.7 MiB，无新增 OOM。电脑 Chrome 与小米 PWA 页面验收按用户反馈通过，范围和证据见 [实施状态](implementation-status.md#2026-11-01-新闻发布终态审核本批验收通过)。

## 发布验收

新闻与对应日历事件的人工确认关联已部署并完成本批验收，双向入口、快照、修订提示及验证边界见 [关联接口](calendar-links-api.md)；与上述跨来源报道关联分别保存。双端关联显示与双向跳转按用户反馈通过，完整功能、采集与资源观察终态已审核。

使用 `scripts/publish-news.ps1`，共享日历发布的备份和失败回滚流程。脚本先将冻结备份与实时数据库核对：原条目身份、首次记录、正文/链接/发布时间及旧修订需保留，正常采集产生的新版本必须有原版证据。旧时间字段仍保持未知；新新闻编号不复用。

分类完成后进行服务重启及约 65 分钟观察。每分钟使用服务器本机短时会话检查未登录拒绝、列表、分页、详情、来源筛选、增量水位及 `no-store`；每五秒记录资源，沿用 96 MiB 服务上限、64 MiB 主机余量及无新增 OOM 的准入。报告分别保存安装阶段主机内存读数、索引阶段峰值和重启后的资源，避免重启后丢失之前的峰值证据。至少两轮 TrendRadar 采集和真实新闻变更需有证据；上游失败次数、缺口和恢复时间单独保留，最终仍需审核。

该专项不重复两个交易日的延迟统计，不签收 AI 负载或日历下次六小时同步。若只有 `queued/deploying` 初始报告，先用 `-Report` 获取后续进度；进入 `observing / news_and_resources` 后，电脑 Chrome 和小米 PWA 再刷新，验收筛选、来源链接、修订、详情返回和未知时间。`completed_for_review` 是机器检查结果，页面及资源报告审核仍是独立步骤。

来源级采集状态与故障历史使用独立只读接口，见 [来源健康接口](source-health-api.md)；数据库导入结果仍保留在 `news/meta` 的 `channels` 中。
