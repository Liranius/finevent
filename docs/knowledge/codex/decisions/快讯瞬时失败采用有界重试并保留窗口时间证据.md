# 快讯瞬时失败采用有界重试并保留窗口时间证据

用户授权先修正脱敏与过时文档，再处理快讯超时重试和延迟证据。既有真实观察发现过 320 秒轮询间隔；统一五分钟失败等待会放大偶发超时的影响，而单凭未发现窗口缺口无法解释长尾新闻。本笔记记录该授权下的实现方案。正常采集和逐页证据已在生产验证；真实故障恢复及超长延迟归因仍需相应样本，具体行为由源码和新闻接口文档维护。

正常采集周期保持不变，只对网络、超时、正文读取中断和暂时服务故障采用逐步退避；限流及有效 Retry-After 继续约束下一次请求。失败序列从持久化轮询重建，重启不清零。没有采用请求内部连续重试或全面提高采集频率，以免放大持续故障、阻塞导入或增加稳定期请求量。TrendRadar 与付费 AI 的调度独立。

逐页保留起止时间、失败类别、响应摘要和有界条目 ID/发布时间，可核对在相邻窗口中出现的变化。原始正文不重复存储，证据保留期短于轮询记录，降低存储增长；代价是无法仅凭摘要重新解析过去的完整响应。截断、失败、旧记录及已清理证据保持可辨，不将缺失证据当作没有新闻。失败后的正常轮询不自动关闭历史缺口。

延迟统计使用首次发现时实际保存的发布时间，而不是来源后来修订的时间。缺少首版证据的历史条目归为未知，不反推其原值。既有新闻详情仍展示当前来源时间及版本证据，统计口径与当前内容各有用途。

## Observations

- [decision] 在用户已授权的修复范围内，采用持久化、有上限的瞬时失败退避，保留正常采集节奏及限流约束。
- [rationale] 缩短偶发失败的恢复等待，同时避免持续故障造成密集请求。
- [consequence] 窗口元数据帮助定位延迟，但不等于原始全文存档或上游完整覆盖证明。
- [constraint] 首次生产窗口未出现自然请求失败或超过五分钟的新增报道，不能据此判定退避效果或历史长尾原因。窗口结果和剩余 TODO 见 docs/implementation-status.md。
